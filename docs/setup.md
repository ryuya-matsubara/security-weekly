# ChatGPTでのスケジュール登録手順

更新日: 2026-10-23

## このリポジトリの範囲
調査仕様とJSON交換形式を管理する。閲覧画面、実ニュースの週報、自動配信プログラム、GitHub Actionsは今回含めない。
リポジトリは非公開のままでよい。生成した週報はタスク結果から取得し、将来の閲覧画面へ手動インポートする。

## 1. GitHub接続と環境
1. ChatGPTの設定でGitHubのプラグイン/アプリを接続する。表示名は環境によって異なる。
2. GitHub側の連携アプリのリポジトリアクセスにryuya-matsubara/security-weeklyを追加する。
3. ChatGPT WebのWorkで新しいチャットを開き、GitHub連携・Web検索・ファイル作成/永続保存が利用できる構成を選ぶ。
4. 「Scheduled / スケジュール済み」が利用できることを確認する。なければアカウント・ワークスペースの提供状況を確認する。CLI/IDEのみでは登録画面を使えない。

ローカルプロジェクトを使うデスクトップ側の自動化とは区別する。自宅PC常時起動を前提にしないWeb側のタスクを選ぶ。
この会話でGitHubリポジトリの読み書きが成功しても、将来の定期実行でGitHub/Web検索/ファイル保存が利用できることまで確認済みとはならない。

## 2. 登録前の確認（本人が許可した場合だけ）
GitHubから必須4ファイルを同一コミットで全文取得できるかを確認し、次に1回分の調査とJSON保存・iPhoneからのダウンロードを確認する。
これは動作確認に当たるため、本人の事前許可なく自動でRun nowや調査テストを実行しない。
通常チャットの成功だけで定期実行の成功とみなさず、本人が許可した最初の定期実行結果も確認する。

## 3. タスクの登録
初期提案: 毎週月曜07:00、Asia/Tokyo。曜日・時刻は変更可。このリポジトリ作成時点ではタスク未登録。
1. 独立した定期タスクとして登録する。各回の必須仕様はGitHubから読み直す。
2. prompts/task-prompt.mdの本文を、タスクの実行プロンプトに全文保存する。「task-prompt.mdを見て」の一文だけにはしない。
3. スケジュール欄を毎週月曜07:00、日本時間にする。
4. 自然文から登録する場合は、以下の依頼文の末尾にtask-prompt.mdの本文を貼り付ける。

「独立した定期タスク『セキュリティ週報』を作成してください。毎週月曜日07:00、タイムゾーンAsia/Tokyoで実行してください。今すぐの試行実行はしないでください。毎回の実行指示には、以下の全文を保存してください。」

5. 作成結果を開き、繰り返し・タイムゾーン・次回実行・プロンプト全文を確認する。作成完了が表示されなければ登録済みと扱わない。
6. タスクで外部アプリの接続・再接続・承認が必要と表示されたら、先に解決する。定期実行で解決できると仮定して先へ進めない。

参照する仕様は毎回mainから読むため、4仕様ファイルの内容変更は次回に反映される。ファイルパスやタスクの実行方法を変えた場合、保存済みプロンプトも更新する。
prompts/task-prompt.mdだけを編集しても、登録済みタスクのプロンプト本文は自動更新されない。

## 4. 通知とiPhoneでの取得
1. ChatGPTの設定→通知で、タスクに利用できるプッシュ通知を有効にする。メール通知が利用できる場合は選択可。
2. iPhoneの設定でもChatGPTの通知を許可する。
3. 完了通知から結果を開き、JSONの実ファイルリンクをタップする。
4. 共有メニュー等から「ファイルに保存」し、将来の閲覧画面でそのJSONを選択する。
標準の通知メールはGmail連携から本人名義でメールを送る処理とは別。添付メールやLINE連携は初期運用に含めない。

## 5. 更新・保守
- spec/research-policy.md: 編集ルールを更新しpolicy_versionを上げる。
- spec/sources.json: 情報源・人物を更新しsources_versionを上げる。
- spec/report.schema.json: JSON形式の変更時にschema_versionと完成例を合わせる。
- spec/sample-report.json: is_example=trueを維持する。実ニュースを偽装しない。
- prompts/task-prompt.md: 起動時の指示を変更したら、タスク側にも同じ変更を登録する。
- 各週報のspec.commit_shaで、実際に使用したGitHubの版を追跡できる。
- 閲覧画面は将来schema_versionを確認し、未対応の形式やis_example=trueを適切に扱う。

## 6. 失敗時
- GitHub取得失敗: リポジトリアクセスとパスを確認。公開Web検索で非公開本文を代用しない。
- 仕様取得途中の失敗: 成功したファイルだけで調査を続行しない。
- 情報源の一部取得失敗: coverageに記録しpartialとして出力。
- ファイル作成/保存不可: 結果に明示。リンクだけを捏造しない。保存可能な環境に構成し直す。
- 通知なし: Scheduledで実行状態と結果を確認。通知設定と実行失敗を区別する。
- 機械検証未実施: machine_validation=not_run。人の事前許可がある場合だけ検証プログラムを実行する。
